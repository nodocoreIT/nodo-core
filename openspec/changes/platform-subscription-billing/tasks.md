Idempotent: upserts `client_unit_subscriptions` keyed on `client_unit_id`. Typed failure reasons: `missing_token | unit_not_found | unit_not_enabled | plan_not_found | payer_email_missing | fx_unavailable | mp_rejected`. - [x] 5.2 Added `nodo-landing/app/api/mp/subscription-webhook/route.ts` (separate route from any existing clinica webhook) + supporting `nodo-landing/lib/billing/{mp-client,mp-webhook-verify,mp-webhook-handler,billing-time}.ts`. Signature validated via `verifyMpWebhookSignature` (HMAC-SHA256 over `id:{dataId};request-id:{xRequestId};ts:{ts};`, `timingSafeEqual` compare) against a **separate** `LANDING_MERCADOPAGO_WEBHOOK_SECRET` — same algorithm as nodo-clinica's `verifyMercadoPagoWebhookSignature` (MP's generic webhook v2 scheme, reimplemented independently per app since each has its own secret); like clinica's pattern, validation is skipped (not failed closed) only when the secret env var isn't configured. Handles two MP topics: `subscription_authorized_payment` (an individual charge invoice — confirmed the real `GET /authorized_payments/{id}` response shape via MP's official API reference: `preapproval_id`, `transaction_amount`, `debit_date`, and the actual charge outcome nested under `payment.status`, distinct from the invoice-level `status`) and `subscription_preapproval` (overall Preapproval status change). On an `approved` payment: idempotent insert into `subscription_payments` (dedupes by existing `mp_payment_id` for the same `subscription_id`+`cycle_key` before assigning the next `attempt_no`) and resets `client_unit_subscriptions.cycle_started_at`/`next_due_at` from `debit_date` (**not** the original anniversary — verified in tests). On anything else: records the attempt only, **never** flips `client_units.status` — that's explicitly left to the reconciliation job (5.3), since a single webhook event can't distinguish a mid-retry rejection from an exhausted one. The `subscription_preapproval` topic only ever updates `client_unit_subscriptions`'s own tracking status (active/paused/past_due), never touches `client_units` either. Ref: spec `platform-billing` — Reacting to MP's Recurring Billing Outcome, Successful Payment Resets the Cycle.
- [x] 5.3 Added `nodo-landing/app/api/cron/billing-reconciliation/route.ts` + `nodo-landing/lib/billing/billing-reconciliation.ts`. `Authorization: Bearer CRON_SECRET` (same pattern as `backup-orgs`); ships **off by default**, only runs when `BILLING_RECONCILIATION_ENABLED=true` (task-required feature flag). Selects `client_unit_subscriptions` where `status='active'` and `cycle_started_at <= now - BILLING_RECONCILIATION_GRACE_DAYS` (default 30, env-overridable); skips if an `approved` `subscription_payments` row already exists for that cycle, or if there's no `mp_preapproval_id` yet, or if MP's `getPreapproval` still reports `authorized` (webhook may just be delayed — never flips on a hunch). Only on a confirmed terminal MP state does it flip `client_units.status='impago'` — the **one and only place** in this whole change that makes that transition. **On "for update skip locked"**: PostgREST doesn't expose row-level locking directly, so this uses a single atomic conditional `UPDATE client_units SET status='impago' WHERE id=X AND status != 'impago' RETURNING ...` instead — Postgres already row-locks for that statement's duration, giving the same "no double-write on overlap" and "re-run is a no-op" guarantees without a dedicated locking migration for a job that ships flagged off (documented in a code comment; authorized_payments-level retry-cadence inspection beyond `getPreapproval`'s top-level status remains the same open verification item design.md already flagged). Ref: spec `platform-billing` — day-30 checkpoint, idempotent re-run scenario.
- [x] 5.4 Added `sendPaymentOverdueEmail` to `nodo-landing/lib/mail.ts` (same brand-per-nodo template pattern as `sendAccountEnabledEmail`), sent from the reconciliation job exactly once per flip: because the `impago` transition itself is idempotent (guarded by the same conditional UPDATE as 5.3), a re-run that finds the unit already `impago` sends zero rows back and the email call is never reached.
